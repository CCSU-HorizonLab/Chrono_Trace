# Chrono Trace G1：联系人知识到建议生成闭环

## 文档状态

- **阶段**：G1 施工单（生成侧闭环）
- **建立日期**：2026-09-28
- **前置版本**：v1.2.0-beta.1
- **当前结论**：记忆写入质量已有明显改善，但“记忆/画像/关系策略/好感分析 → 最终建议”仍不是稳定闭环。
- **本阶段原则**：先修上下文路由、任务识别和最终 prompt 证据链，再讨论扩大记忆数量或更换模型。
- **本阶段范围**：手动建议、自动建议、记忆问答、邀约策划、关系讨论及其最终生成 prompt。
- **不在本阶段**：重做全部事实抽取、更换模型、训练模型、把反馈候选直接转为正式偏好。

## 一、当前情况与证据

### 1. 已经改善的部分

- LLM 事实抽取、代词残留拦截、消费类话题过滤、事实演变链和历史回补已经落地。
- 当前联系人事实不再是早期大量单轮碎片，已有较多自包含事实、关系边界和偏好槽。
- 联系人画像、用户表达画像、关系状态和偏好策略已经具备独立存储与注入代码。
- 768 维 embedding、索引状态、事实禁用和策略刷新链路已有实现。

这些结论只说明写入侧和基础设施有进展，不等于建议生成已经正确使用这些数据。

### 2. 已确认的生成侧问题

#### 2.1 任务识别与知识使用耦合

当前 `direct_reply` 同时决定输出格式和是否注入关系知识。用户输入“我想约她打游戏”时，系统可能将其判为直接问 AI，而不是建议任务；最终 prompt 会要求：

- `summary` 为空；
- `speeches` 为空；
- 不生成建议卡片；
- 跳过关系策略、联系人画像、偏好和用户风格块。

因此会出现“检索日志有参考 ID，但模型没有拿到可用于建议的关系数据”。

#### 2.2 联系人范围不是所有入口的必需字段

部分自动建议日志出现 `conversation_id=None`、`missing_scope`，但仍继续生成画像或普通建议。显示名只能作为兼容解析，不能替代稳定的 `account_wxid + conversation_id`。

同名联系人、跨账号切换、前端切页和自动触发都可能造成“画像属于当前联系人，RAG 却没有联系人范围”的不一致。

#### 2.3 最近消息会被系统通知污染

生成 prompt 的最近消息窗口可能被转账、收款等系统事件占满。模型随后把“只看到转账”解释成对方低回应、冷淡或没有接话，进而生成错误的关系建议。

写入侧过滤系统消息，不代表生成侧最近消息已经过滤；两条链路必须分别验收。

#### 2.4 脱敏可能损失关键事实

部分游戏名被地址模式误替换为 `[ADDRESS_xxx]`。这会导致“已经召回事实，但模型看不到事实核心对象”。隐私保护不能以损失可理解性为代价；脱敏后若核心内容不可用，应标记为不可引用证据，而不是继续显示为有效命中。

#### 2.5 好感分析尚未成为可解释的关系信号

好感分析目前主要被压缩为 `cold / neutral / warm` 等风格约束，缺少：

- 分析时间和覆盖窗口；
- 数据量与置信度；
- 趋势变化；
- 能支持的行为建议；
- 明确不能推出的结论。

聊天数量多不能直接等同于亲密度；好感分数也不能单独授权推进关系。

#### 2.6 已参考不等于已发送

当前日志已经能记录候选事实、关系策略和偏好 ID，但仍需区分：

```text
召回 → 选中 → 脱敏后实际发送 → 模型输出实际使用
```

前端 badge 只能依据“实际发送清单”，不能依据中间 context 或候选数量显示“已参考”。

## 二、本阶段目标

给定同一个联系人和同一个输入，系统必须做到：

1. 正确识别用户是在问历史、求回复建议，还是讨论关系；
2. 始终绑定正确的 `account_wxid + conversation_id`；
3. 只选当前任务相关的事实、边界、偏好和画像；
4. 经过脱敏后仍保留可理解的核心信息；
5. 将实际发送给模型的数据完整记录下来；
6. 生成结果可追溯、可解释、可安全降级；
7. 同一批输入在 no-RAG、旧链路和 G1 链路之间可重复对照。

本阶段首个目标样例：

> 对昕输入“我想约她打游戏”，系统应进入建议任务，绑定昕，优先使用共同游戏/对方游戏偏好和相关边界，生成可发送的邀约话术，并记录实际使用的事实与策略 ID。

## 三、任务拆分

### G0：冻结验收依据

- [ ] 从真实日志建立首批 24 条诊断样例。
- [ ] 覆盖任务切换、联系人绑定、通知污染、脱敏误伤、策略适配和缺失降级。
- [ ] 每条样例记录预期任务、输出形式、必须使用/禁止使用的数据及安全边界。
- [ ] 保存改造前的任务判定、召回 ID、最终脱敏 prompt、模型输出和人工判定。
- [ ] 固定模型、配置、数据库快照、代码版本和评测版本。

**验收**：同一输入可重复回放；所有失败可归类为路由、选择、脱敏、生成或安全降级问题。

### G1：统一联系人上下文

- [ ] 所有生成入口统一传递 `account_wxid`、`conversation_id`、`request_id`、`entrypoint`。
- [ ] 后端校验会话属于当前账号。
- [ ] 显示名只用于展示和兼容解析。
- [ ] 同名或歧义联系人不得自动选取。
- [ ] 缺失联系人范围时安全降级为通用帮助，并记录 `missing_scope`。
- [ ] 自动、手动、开场、实时回复入口使用同一上下文装配函数。

**单测**：同名联系人、多账号、无效 ID、跨联系人切换、缺失画像、缺失分析结果。

**验收**：同一联系人不同入口的 fact、profile、policy 来源一致；跨联系人注入为零。

### G2：拆分任务识别、输出格式和知识需求

- [ ] 将当前单一模式拆成：

  ```text
  task：记忆问答 / 回复建议 / 邀约策划 / 关系讨论 / 普通问答
  output：直接回答 / 建议卡片 / 回答附话术
  knowledge_needs：事实 / 对方画像 / 用户风格 / 关系信号
  ```

- [ ] “我们玩过什么游戏”进入事实问答。
- [ ] “我想约她打游戏”进入邀约建议。
- [ ] “没有建议么”继承上一轮建议任务并修正输出。
- [ ] 关系讨论即使直接回答，也允许使用相关画像和证据。
- [ ] 纯历史问答不强行注入用户口头禅和建议风格。
- [ ] 不确定时优先保持安全输出，不擅自生成代发话术。

**单测**：三轮任务切换、否定句、建议追问、普通闲聊、直接问 AI 和代用户回复的区分。

**验收**：不存在“用户明确求建议但 prompt 强制 speeches 为空”的冲突。

### G3：净化生成侧近期对话

- [ ] 区分人工聊天、转账/收款事件、系统通知和不可解析消息。
- [ ] 通知不占用有效聊天窗口名额。
- [ ] 转账作为事件摘要时不得伪装成对方主动发言。
- [ ] 纯通知窗口不得推导冷淡、拒绝、已读不回等关系结论。
- [ ] 正常文字提及转账仍保留。
- [ ] 回复率、回复间隔和情绪统计使用正确的消息配对。

**验收**：转账通知密集的窗口仍能保留有效聊天；模型不再因通知得出错误关系判断。

### G4：保证脱敏后的证据仍可用

- [ ] 增加游戏名、地名、真实地址、电话号码的脱敏正反例。
- [ ] 修复地址规则误伤“路易吉鬼屋”等非地址实体。
- [ ] 脱敏后检查事实的核心对象是否仍存在。
- [ ] 核心对象丢失时记录 `evidence_redacted_unusable`，不得计为有效注入。
- [ ] 远程脱敏失败继续 fail-closed，不得回退发送原文。

**验收**：隐私规则不回退；游戏名、项目名等关键实体在远程 prompt 中保持可理解。

### G5：按任务选择知识并处理冲突

- [ ] 选择顺序固定为：当前目标 → 相关事实 → 直接边界 → 相关偏好 → 必要关系背景 → 表达风格。
- [ ] 邀约游戏优先召回共同游戏和对方游戏偏好，不让贴膜、穿衣等无关偏好抢占预算。
- [ ] 画像 `interests` 作为兴趣线索，不自动升级为“共同经历”。
- [ ] 增加知识项的来源、时间、新鲜度、置信度和适用场景。
- [ ] 明确边界和当前表态优先于历史画像。
- [ ] 好感分析以带时间和不确定性的关系信号注入，不能直接等同亲密度。
- [ ] 缺失数据输出 `unknown`，不生成“没有昵称习惯”等伪结论。
- [ ] 解决画像、量化风格约束和默认规则之间的冲突。

**验收**：同一联系人在游戏邀约、冲突降温、项目协作和普通闲聊中选择不同知识集合。

### G6：建立最终 prompt 发送审计

- [ ] 生成 `request_id → suggestion_id → retrieval_log_id` 关联。
- [ ] 记录实际发送的 `fact_ids`、`policy_ids`、偏好 ID、画像版本、分析版本。
- [ ] 记录候选被排除的原因：不相关、预算不足、敏感、脱敏失真、任务不匹配或过期。
- [ ] 在脱敏完成后计算最终 prompt hash。
- [ ] 普通日志只记录 ID、版本、hash 和原因；诊断模式才保存脱敏 prompt 快照。
- [ ] 前端 badge 只显示“实际发送”，并区分历史事实、关系策略、当前上下文和未命中。

**验收**：每条“已参考”都能定位到最终 prompt 中的具体块；候选命中但未注入时 UI 不得显示已参考。

### G7：端到端回放与发布门禁

- [ ] 对 G0 样例运行 no-RAG、现有链路和 G1 链路三路对照。
- [ ] 人工评估任务识别、联系人隔离、证据使用、边界遵守、无关旧事、可发送性和隐私。
- [ ] 记录延迟、超时、降级率和失败原因。
- [ ] 对模型输出使用脱敏 evidence 做 `entailed / contradicted / unknown` 判定。
- [ ] 结果保存模型版本、prompt 版本、评测版本和原始判定。
- [ ] 安全指标任何回退时按联系人切回旧读侧或 `inherit`。

**发布条件**：任务契约、联系人隔离、隐私红线、最终发送清单一致性全部通过；效果指标以冻结人工集基线为准，不用旧的 9/10 自洽性数字替代。

## 四、数据流与优先级

```text
输入/当前对话
    ↓
联系人范围解析与校验
    ↓
任务识别（问历史 / 求建议 / 关系讨论）
    ↓
知识需求规划
    ↓
事实、边界、偏好、画像、好感信号召回
    ↓
相关性/安全/新鲜度/预算筛选
    ↓
脱敏与核心实体完整性检查
    ↓
最终 prompt + 发送清单
    ↓
模型输出校验与可发送性过滤
    ↓
建议、日志、反馈归因
```

知识优先级固定为：

```text
安全与明确边界
> 当前明确表态与用户目标
> 当前相关事实
> 关系策略与偏好
> 联系人画像和好感趋势
> 用户表达风格
> 缺省规则
```

## 五、回滚与安全规则

- RAG、画像或好感分析失败不得阻塞建议生成。
- 联系人范围不确定时不得注入历史知识。
- 脱敏失败不得发送远程原文。
- 敏感事实不得进入 prompt。
- 事实冲突时保留审计链，不直接覆盖历史证据。
- G1 可按联系人切回旧文档读侧或 `inherit`。
- 失败回滚不删除事实、策略、发送清单和诊断日志。

## 七、阶段完成定义

G1 只有在以下条件同时满足时才能标记完成：

- [ ] G0 诊断集冻结并可重复回放；
- [ ] 所有生成入口具备稳定联系人范围；
- [ ] 任务识别与输出格式不再互相误伤；
- [ ] 近期对话不会被系统通知主导；
- [ ] 脱敏后关键事实仍可理解；
- [ ] 记忆、画像、关系策略和好感信号按任务正确注入；
- [ ] 最终发送清单与实际 prompt 一致；
- [ ] 24 条诊断样例通过安全和契约门禁；
- [ ] 至少一轮 no-RAG/旧链路/G1 三路端到端对照完成；
- [ ] 失败时可按联系人回滚，且事实和审计数据保留。

在这些条件完成前，只能称为“G1 施工中”或“生成链路部分可用”，不能称为“联系人记忆已完整生效”。
