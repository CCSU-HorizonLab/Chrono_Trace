# Chrono Trace v2.1.0 发布说明

**版本**:v2.1.0(功能版) ｜ **日期**:2026-10-19 ｜ **上一版本**:v2.0.0(2026-10-19)

两条主线:**实时监听全平台统一为数据库监听**(Windows 弃用 UIA 采集链);**实时消息上屏延迟 ~4.5s → ~1s**(贴物理极限)。

## 实时监听:全平台统一数据库监听(架构)

- **Windows 弃用 UIA 采集链**:不再向微信界面注入自动化读取消息,与 Linux 统一走 db_watch——直接监听微信加密库文件(mtime + WAL 增量解密)。UIA 链的无破坏修复、辅助桥激活、自动恢复确认弹窗等整套机制随之移除,前端文案统一为「数据监听」语义。
- **不再依赖微信界面状态**:最小化、后台、无障碍服务开关都与采集无关;消除 UIA 树读取的性能抖动与界面激活类故障。
- 双平台同一套行为与缺陷口径:Windows 无 inotify 时自动降级 stat 轮询,无需配置。
- 修复:wxauto4 垫片补 provider.initialize,未初始化时 open_chat 静默找不到消息表。

## 实时上屏 ~4.5s → ~1s(延迟,真机实测)

按五段延迟构成逐段落地(实测机型:外置机械盘):

- **WAL-only 快路径**:主库文件未变时跳过全库逐页重读+SHA1,单分片刷新 0.4~0.6s → **0.14~0.2s**。checkpoint 写主库时自动回全量路径对账(天然对账点,无定时全量开销)。
- **refresh 并发锁**:消除轮询线程与后台刷新并发写同一 sidecar 的竞态(tmp 替换 Errno 2 / 文件撕裂);并发刷新实测零错误。
- **每轮只刷目标分片**:fts 索引库等无关分片的刷新(300~600ms)不再挡在消息查询前,由定位聊天前的全分片刷统一兜底;帧撕裂重放(reconcile)周期同样只覆盖目标分片。
- **轮询提速**:采集轮询 0.3s → 0.05s,Linux 下 inotify 事件毫秒级唤醒;无变化轮询微秒级短路。
- **evaluate_js 推送通道**:消息落库即推送前端上屏,不再等 3s 前端轮询;3s 轮询保留作对账兜底(数字 id 幂等去重,不重复显示)。
- **sidecar 跨启动保留**:停止监听不再删除解密快照,「停止 → 再启动」从全量重解密(实测慢盘 ~47s,盘速相关)变为**秒级续用**。
- **显示与分析解耦**:消息先上屏,情感分析后台执行且单次推理(此前同一条消息跑两遍)。

实测口径:事件 → 应用内消息 buffer 稳态 **0.03~0.07s**(首响 ~0.4s,checkpoint 波 ~0.5s);端到端 ≈ 微信写库 0.7~0.9s(不可控)+ 应用侧 ~0.1s ≈ **0.8~1.0s**。

## 悬浮窗稳定性(Windows)

- **样式切换看门狗**:SetWindowLong 跨线程挂起只损失一次样式切换,不再卡死应用。
- **SetWindowPos 异步化**:跨线程同步消息挂起防卡死,定位改投递异步执行。

## 升级须知

- UIA 采集链及其激活/自动恢复机制整体移除,Windows 采集行为与 Linux 完全一致;监听设置(对象、触发模式、建议配置)语义不变。
- 实时消息进入 RAG 长期记忆的时机仍在回溯落库之后(增量游标口径与 2.0.0 一致),监听期间不实时入记忆。
- 首次启动新版本监听会重建一次解密快照(一次性,数十秒量级,盘速相关);此后跨启动续用。
